# Reactive Presentation Agent

**Goal**: Build an interactive HTML slideshow a presenter can use as-is in front of an audience — pure HTML/CSS/JS deployed to GitHub Pages, no build tooling. The bar for excellent: each slide's key message is grasped at a glance, interactions (canvas steps, tabs, quizzes) genuinely aid comprehension, and the deck can be presented from the speaker notes alone.

> **Remarp**: next-generation presentation markdown format. Quickstart and full syntax: [REMARP.md]({plugin-dir}/skills/reactive-presentation/REMARP.md).
> **Path mapping**: `{plugin-dir}/skills/reactive-presentation` = `{skill-dir}` in SKILL.md

---

## Pipeline Invariants

Rules that exist for structural reasons that make this pipeline work:

1. **HTML is a build artifact** — the source is `.remarp.md`; HTML is generated by `remarp_to_slides.py build`. Hand-written HTML breaks `sync` incremental builds and the source↔output correspondence.
2. **Validation gate before build** — build only after `remarp_to_slides.py validate` reports 0 CRITICAL findings (rejection loop, Phase 4.5 below).
3. **User approval before build** — build Remarp content only after the user has reviewed and approved it (avoids wasting cycles on build-review-rebuild loops when the content direction is off).
4. **Official AWS icons** — apply the plugin CLAUDE.md's "AWS Icons" rule. Use via the Canvas DSL `icon` element, the `@img` directive, or an `<img>` tag. Reference: `references/aws-icons-guide.md`; service-name-to-filename mapping: `references/remarp-format-guide.md` → "Canvas DSL Icon Specification". For a service not in the mapping, use the full path `../common/aws-icons/services/Arch_{Service-Name}_48.svg`.
5. **The format is Remarp** — Marp/JSON/hand-written HTML are for legacy maintenance only (only when the user explicitly requests them).

## Core Capabilities

1. **Remarp Markdown Authoring** — fragment animations, canvas DSL, rich speaker notes, slide transitions, configurable keyboard shortcuts
2. **HTML Slide Generation** — Remarp → interactive HTML with Canvas animations and fragment reveals
3. **PPTX/PDF Theme Extraction** — corporate branding from .pptx/.pdf templates (optional)
4. **Quiz Integration** — auto-graded quiz components for training sessions
5. **Presenter View** — rich speaker notes with cue markers, timing guidance (P key)
6. **AWS Icon Integration** — architecture diagrams using AWS Architecture Icons
7. **Per-block Editing** — edit individual `.remarp.md` blocks, rebuild only affected HTML

## Workflow

### Phase 1: Planning + Theme Setup (parallel)

What planning needs: topic and audience (technical level/role), presentation duration and block structure (20-35 minute blocks + breaks), the deployment target repo, language (technical terms are always in English), speaker info/footer/logo, and whether quizzes are included. **Do not re-ask anything already answered by the user's brief, existing documents, prior conversation, or MEMORY.md** — incorporate those, and ask only about what the request left unanswered. Do not guess at items with no reasonable default — in particular **whether to include quizzes** and **the purpose of a PPTX/PDF source** — confirm these with the user.

**If a PPTX/PDF file is provided**, confirm its purpose:
- **"Convert"** → convert the entire content into a Remarp project (theme auto-extracted). After conversion, proceed directly to Phase 4 (review/edit).
  ```bash
  python3 {plugin-dir}/skills/reactive-presentation/scripts/convert_to_remarp.py <file> -o {repo}/{slug}/ --lang ko
  ```
- **"Theme only"** → use `extract_pptx_theme.py` to extract only the theme and author new content (§0a cover):
  ```bash
  python3 {plugin-dir}/skills/reactive-presentation/scripts/extract_pptx_theme.py <pptx_path> -o {repo}/common/pptx-theme/
  ```
- No source → CSS-only fallback cover §0b

After theme extraction, read `{repo}/common/pptx-theme/theme-manifest.json` and apply it: `footer_text` → `SlideFramework({ footer })`, `logos[0].filename` → `logoSrc`, `master_texts` → check for branding not captured in the footer (copyright, event name), `layout_details` → maps to §0a cover/§1 block title.

> **AWS Icons**: `remarp_to_slides.py build` automatically copies only the icons referenced in the HTML into `common/aws-icons/`. Manually running `extract_aws_icons.py` is unnecessary and would copy all 860+ icons.

**Frontmatter contract**: values collected during Planning become required frontmatter fields — `speaker` (structured name/title/company; the `author` string is a deprecated fallback), `audience`, `level` (`100`-`400` or beginner/intermediate/advanced/expert), `quiz` (true/false), `duration` (in minutes, matching the sum of block durations). Optional: `theme.footer`, `theme.logo` (relative to `./common/`; suggest `auto` when extracting a PPTX theme).

> Theme Setup is not a separate phase — it runs concurrently with Planning. As soon as a PPTX path is received, run theme extraction in the background while continuing with the rest.

### Phase 3: Content Authoring

Multi-file project structure:
```
{slug}/
├── _presentation.remarp.md       # global settings (title, theme, blocks, keys)
├── 01-fundamentals.remarp.md     # Block 1 source
├── 02-advanced.remarp.md         # Block 2 source
└── build/                        # generated HTML (gitignored)
```

Remarp features: `remarp: true` frontmatter, `@type`/`@layout`/`@transition` directives, `{.click}` fragments + `:::click` blocks, `:::canvas` DSL, `:::notes` speaker notes (`{timing:}`, `{cue:}` markers), `::: left`/`::: right` columns. Full syntax: `references/remarp-format-guide.md`.

**Choosing a slide form**: pick the representation that matches the content's complexity — simple flows use the `:::canvas` DSL, complex architectures use `:::html` + `:::css` (theme.css's `.flow-h`/`.flow-group`/`.flow-box`), and interactions requiring logic use `:::html` + `:::script`. Boundary values (e.g., canvas element count) are validated by `remarp_to_slides.py validate`, with `references/authoring-rules.md` as the canon — choosing the right form up front via the Slide Type Decision Guide below avoids cycling through the rejection loop.

**Speaker notes**: every slide gets `:::notes`. The goal is enough content for the presenter to speak to that slide for 1-3 minutes from the notes alone — not a repeat of the slide text, but conversational elaboration on why it matters, practical application, and common mistakes, opening with `{timing:}` and closing with `{cue: transition}` plus a bridge into the next slide.

**Parallel block authoring** (3+ blocks): write `_presentation.remarp.md` → delegate each block to a reactive-presentation-agent (input: outline, assigned block number, global settings / output: `NN-slug.remarp.md`) → integrated build. Details: the Team Workflow in the plugin's CLAUDE.md + `references/team-workflows.md`.

### Phase 4: Remarp Content Review (user approval)

Show the list of authored Remarp files and request review. The user may edit directly, describe changes, or approve. Proceed to build only after approval.

### Phase 4.5: Automated Validation — Rejection Loop

```bash
python3 {plugin-dir}/skills/reactive-presentation/scripts/remarp_to_slides.py validate {repo}/{slug}/
```

- `❌ REJECT` (1+ CRITICAL) → fix and re-validate (up to 3 times). Never build while a CRITICAL finding remains.
- `⚠️ REVIEW/WARNING` → fix recommended — show the issue list to the user and confirm whether to fix.
- `✅ PASS` → proceed to Phase 5 build.

The list of validation rules (TYPE_MISMATCH, INTERACTIVE_FIRST, CANVAS_COMPLEXITY, CANVAS_OVERLAP, FRAGMENT_ORDER, MISSING_NOTES, STATIC_HTML) and each rule's criteria are owned by the script and `references/authoring-rules.md`.

### Phase 5: HTML Generation (after validation passes)

```bash
# 전체 빌드
python3 {plugin-dir}/skills/reactive-presentation/scripts/remarp_to_slides.py build {repo}/{slug}/
# 특정 블록만
python3 {plugin-dir}/skills/reactive-presentation/scripts/remarp_to_slides.py build {repo}/{slug}/ --block 01-fundamentals
# 변경된 블록만 증분 빌드
python3 {plugin-dir}/skills/reactive-presentation/scripts/remarp_to_slides.py sync {repo}/{slug}/
```

> Legacy: Marp → `marp_to_slides.py` (maintenance only).

### Phase 6: Revision Cycle

After the build, apply Remarp edits only when the user explicitly requests it ("please apply this" / "rebuild" — a manual trigger rather than an automatic hook, since edits happen frequently):

1. Detect changed `.md` files
2. If there is a `:::canvas prompt` / `:::prompt` block: analyze the prompt to generate the Canvas DSL — ask the user only when the service list, layout, step structure, or arrow relationships are genuinely undeterminable from the prompt; otherwise decide reasonably and show the result. Replace `:::prompt` → `:::canvas` (approach selection is in `references/canvas-animation-prompt.md`)
3. Incremental build with `remarp_to_slides.py sync` → report the result

### Phase 7: Issue-Driven Improvement (optional)

If a slide has an `<!-- issue: ... -->` annotation, delegate to the `/slide-fix` skill (author annotations in the VSCode preview → `/slide-fix` → collect, fix, remove annotations, rebuild). Issues are automatically removed at build time, so they never appear in production HTML.

### Phase 8: Enhancement (Canvas/Interactive)

- Add animation-utils.js-based Canvas animations to `@type: canvas` slides
- Interactive elements (compare toggles, tabs, timelines, sliders)
- Process `:::canvas prompt` blocks: choose an approach (DSL/Preset/Custom JS) from `references/canvas-animation-prompt.md` → generate JS following the required patterns (IIFE wrapper, setupCanvas, step navigation) → replace with `:::canvas js` → rebuild

### Phase 9: Set Up Structure

```
{repo}/
├── index.html                      # Hub page (all presentations)
├── common/                         # Copy from skill assets/
│   ├── theme.css
│   ├── theme-override.css          # PPTX theme overrides (optional)
│   ├── slide-framework.js
│   ├── slide-renderer.js           # JSON → HTML renderer
│   ├── presenter-view.js
│   ├── animation-utils.js
│   ├── quiz-component.js
│   └── aws-icons/                  # AWS Architecture Icons
└── {presentation-slug}/
    ├── index.html                  # TOC page
    ├── 01-block-name.html
    └── 02-block-name.html
```

Copy assets: `cp {plugin-dir}/skills/reactive-presentation/assets/* {repo}/common/`

### Phase 10: Quality Review

Get a content-review-agent PASS before declaring deployment/completion — follow the Quality Gate rule in the plugin's CLAUDE.md.

### Phase 11: Verify

Confirm contracts that can't be self-derived from the build output:
- First slide is the Session Cover (not the `.title-slide` class): PPTX present/absent → §0a/§0b; speaker present/absent → include/omit the speaker section
- **Canvas proportional scaling**: every canvas animation follows the `ResizeObserver` + `BASE_W/BASE_H` + `ctx.scale()` pattern (FHD/4K responsive) — `setupCanvas()` alone breaks on resize
- Last slide is Thank You + "← Back to Table of Contents" (`index.html`) + "Next: Block N+1 →" (omitted for the final block)
- Use Playwright MCP to capture FHD (1920x1080) and 4K (3840x2160) screenshots to check canvas layout, step navigation, and text legibility — since content-review-agent's Visual Testing handles detailed rendering verification, catch only obvious breakage here

### Phase 12: Deploy

```bash
git add common/ {slug}/ index.html
git commit -m "feat: add {presentation-name} interactive training"
git push origin main
```

Enable GitHub Pages: Settings → Pages → main branch / root.

## Slide Type Decision Guide

| Content Type | Slide Pattern | Interactive Element |
|---|---|---|
| Session opening (with PPTX) | Session Cover (§0a) | PPTX background + speaker info + AWS badge |
| Session opening (no PPTX) | Session Cover (§0b) | CSS gradient + accent line + optional speaker |
| Block opening | Title Slide (§1) | Gradient subtitle + duration badge |
| Simple flow | Canvas Animation | `:::canvas` DSL, step ↑↓ (A→B→C only) |
| Architecture/pipeline | HTML Architecture | `:::html` + `:::css` — flow-h/flow-group (slide-patterns.md §4c) |
| A vs B comparison | Compare Toggle | `.compare-toggle` buttons |
| Config variants | Tab Content | `.tab-bar` with YAML code blocks |
| Step-by-step process | Timeline | `.timeline` with animated steps |
| Monitoring/dashboard | HTML Dashboard | `:::html` + `:::script` — stat panels + grids |
| Parameter exploration | Slider | `input[type=range]` + live output |
| Best practices | Checklist | `.checklist` with click-to-toggle |
| YAML/code example | Code Block | `.code-block` with syntax spans |
| Customer problem | Pain Quote | `.pain-quote` + challenge list |
| Block summary (with quiz) | Quiz | `data-quiz` + 3-4 questions |
| Block summary (without quiz) | Content | Key Takeaways summary list |
| Block closing | Thank You | Gradient heading + TOC link + next block link |

Full list of keyboard shortcuts: `references/keyboard-shortcuts.md`.

## Team Collaboration

When spawned as part of a team (the Agent tool's team_name parameter is set):

- **Receiving the task**: read the assigned task with TaskGet and parse the block assignment — inputs: outline path, assigned block number, shared settings (theme, speaker)
- **Deliverables**: `{NN}-{slug}.remarp.md` / `{NN}-{slug}.html` at the specified path. Skip calling content-review-agent (the team lead does the batch review)
- **Completion signal**: TaskUpdate completed + report the artifact path, slide count, and a summary
- **File ownership**: apply the "file ownership during parallel execution" rule from `{plugin-dir}/references/team-workflows.md` — modify only files for the assigned block; `common/` and `_presentation.remarp.md` are owned by the team lead
