# AgentCore Format Reference

Specification for Amazon Bedrock AgentCore deployment artifact formats generated by the agentcore-creator plugin.

```json
    "version": "<source-plugin-version>"
  }
}
```

## Agent Code (Strands + BedrockAgentCoreApp)

### agents/<name>.py

AgentCore agents MUST use the `BedrockAgentCoreApp` wrapper with `@app.entrypoint` for deployment:

```python
"""
AgentCore agent: <name>
Converted from Claude Code plugin: <source-plugin>
"""
from pathlib import Path

from strands import Agent
from strands.models.bedrock import BedrockModel
from bedrock_agentcore.runtime import BedrockAgentCoreApp

app = BedrockAgentCoreApp()


@app.entrypoint
async def invoke(payload, context):
    """Handle agent invocation from AgentCore Runtime."""
    prompt_path = Path(__file__).parent / "system-prompts" / "<name>.md"
    system_prompt = prompt_path.read_text(encoding="utf-8")

    model = BedrockModel(
        model_id="<bedrock-model-id>",
        region_name="<region>",
        max_tokens=16000,  # Claude 5 / Opus 4.7+ compatible default; stream for >16K outputs
        # Emitted (not commented out) when the model is effort-capable
        # (Opus 5, Sonnet 5, Opus 4.7/4.8, Sonnet 4.6, Fable 5) -- see EFFORT_CAPABLE_MODELS
        # in scripts/convert_plugin_to_agentcore.py:
        additional_request_fields={"thinking": {"type": "adaptive"}, "output_config": {"effort": "high"}},
    )

    agent = Agent(
        model=model,
        system_prompt=system_prompt,
    )

    result = agent(payload.get("prompt", ""))
    return {"result": str(result)}


if __name__ == "__main__":
    app.run()
```

> **Opus 4.7+ / Sonnet 5 / Fable 5 compatibility note**: these models reject
> `temperature`/`top_p`/`top_k` and `thinking.type: "enabled"` (with `budget_tokens`) —
> both return a 400 error. The `opus` alias currently maps to Opus 5, `sonnet` to Sonnet 5,
> and `fable` to Fable 5 (`MODEL_MAP` is the source). The template above avoids all of that,
> and for models that support `effort`, adaptive thinking + effort is actually turned on in
> the generated code (not just left as a comment). Fable 5 and Opus 5 need a separate check because `stop_reason ==
> "refusal"` comes back as HTTP 200; on Bedrock, a 30-day data-retention
> (`provider_data_sharing`) opt-in is required before you can call it (there is no
> zero-retention option). Details: `references/agentcore-mapping-rules.md` →
> Model-Specific Compatibility Notes.

## Gateway Configuration

### gateway/gateway-config.json

```json
{
  "gatewayName": "<plugin-name>-gateway",
  "description": "API gateway for <plugin-name> tool integrations",
  "targets": [
    {
      "name": "<target-name>",
      "type": "LAMBDA",
      "uri": "arn:aws:lambda:<region>:<account>:function:<function-name>",
      "description": "<target description>"
    }
  ],
  "authorizationType": "AWS_IAM",
  "tags": {
    "source": "claude-code-plugin",
    "plugin": "<source-plugin-name>"
  }
}
```

### Gateway Target Types

| Type | Use Case | Source |
|------|----------|--------|
| `LAMBDA` | Custom tool logic | MCP server command converted to Lambda |
| `OPENAPI` | REST API endpoints | External API integrations |
| `MCP_SERVER` | Direct MCP proxy | Existing MCP servers |
| `SMITHY` | AWS service models | AWS service integrations |

### gateway/targets/<server>.json

```json
{
  "targetName": "<mcp-server-name>",
  "description": "<server description>",
  "sourceCommand": "<original-command>",
  "sourceArgs": ["<original-args>"],
  "environmentVariables": {
    "<VAR>": "${ssm:<parameter-path>}"
  }
}
```

## Memory Configuration

AgentCore Memory uses a dual-store model: STM (Short-Term Memory) for raw events and LTM (Long-Term Memory) for semantic knowledge extraction.

### memory/memory-config.json

```json
{
  "memoryId": "<plugin-name>-memory",
  "description": "Knowledge store for <plugin-name>",
  "stm": {
    "enabled": true,
    "maxEvents": 1000,
    "description": "Raw event storage for conversation history and session data"
  },
  "ltm": {
    "enabled": true,
    "strategies": [
      {
        "name": "<skill-name>-knowledge",
        "description": "Semantic extraction for <skill-name> domain knowledge",
        "namespaces": [
          "/skill/<skill-name>/knowledge/",
          "/skill/<skill-name>/procedures/"
        ],
        "sourceSkill": "<skill-name>",
        "tags": ["<trigger-1>", "<trigger-2>"]
      }
    ]
  },
  "initialKnowledge": {
    "description": "Reference documents pre-loaded into LTM at deployment",
    "sources": [
      {
        "namespace": "/skill/<skill-name>/knowledge/",
        "documents": ["<doc-1>.md", "<doc-2>.md"],
        "sourceDir": "skills/<skill-name>/references/"
      }
    ]
  },
  "tags": {
    "source": "claude-code-plugin",
    "plugin": "<source-plugin-name>"
  }
}
```

### LTM Namespace Design

| Namespace Pattern | Purpose | Example |
|-------------------|---------|---------|
| `/skill/<name>/knowledge/` | Domain knowledge from references | `/skill/ops-troubleshoot/knowledge/` |
| `/skill/<name>/procedures/` | Operational procedures from SKILL.md | `/skill/ops-health-check/procedures/` |
| `/user/facts/` | User-specific facts (auto-extracted) | Runtime-populated |
| `/user/preferences/` | User preferences (auto-extracted) | Runtime-populated |
| `/project/context/` | Project context (auto-extracted) | Runtime-populated |

### memory/strategies/<name>.json

```json
{
  "strategyName": "<skill-name>-extraction",
  "description": "Extract domain knowledge from <skill-name> interactions",
  "extractionRules": [
    {
      "namespace": "/skill/<skill-name>/knowledge/",
      "triggers": ["<keyword-1>", "<keyword-2>"],
      "description": "Extract and store knowledge about <domain>"
    }
  ]
}
```

### Initial Knowledge Documents

Reference documents from Claude Code plugin are chunked and pre-loaded into LTM namespaces at deployment. See `memory-chunking-strategy.md` for chunking algorithm.

```
memory/
├── memory-config.json              # STM/LTM configuration
├── strategies/                     # LTM extraction strategy definitions
│   └── <skill-name>-extraction.json
└── initial-knowledge/              # Pre-loaded reference documents (chunked)
    └── <skill-name>/
        ├── <doc-1>-chunk-1.md
        ├── <doc-1>-chunk-2.md
        └── <doc-2>-chunk-1.md
```

## Lambda Tool Function

### tools/<name>/handler.py

```python
"""
Lambda tool handler: <name>
Converted from MCP server: <source-server-name>
"""
import json


def handler(event, context):
    """Process tool invocation from AgentCore Gateway."""
    action = event.get("action", "")
    parameters = event.get("parameters", {})

    result = execute_tool(action, parameters)

    return {
        "statusCode": 200,
        "body": json.dumps(result)
    }


def execute_tool(action, parameters):
    """Execute the tool action."""
    # Implementation varies by tool type
    return {"status": "success", "result": ""}
```

### tools/<name>/template.yaml

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Description: AgentCore tool function - <name>

Resources:
  ToolFunction:
    Type: AWS::Serverless::Function
    Properties:
      FunctionName: agentcore-tool-<name>
      Handler: handler.handler
      Runtime: python3.12
      Timeout: 30
      MemorySize: 256
      Environment:
        Variables:
          SOURCE_PLUGIN: <source-plugin-name>
      Policies:
        - AWSLambdaBasicExecutionRole
```

## Deployment (agentcore CLI)

AgentCore agents are deployed using the `agentcore` CLI from `bedrock-agentcore-starter-toolkit`:

```bash
# Install CLI
pip install bedrock-agentcore-starter-toolkit

# Configure (region, credentials, project settings)
agentcore configure

# Deploy agent to AgentCore Runtime
agentcore deploy

# Test invocation
agentcore invoke --prompt "Hello, test this agent"

# Check deployment status
agentcore status

# Tear down all resources
agentcore destroy
```

### Deployment Lifecycle

```
agentcore configure → agentcore deploy → agentcore invoke → agentcore status
                                                                    ↓
                                                            agentcore destroy
```

### Post-Deployment: Memory & Gateway Setup

After `agentcore deploy`, use AgentCore MCP tools for additional setup:

| Component | MCP Tool | Action |
|-----------|----------|--------|
| Memory | `memory_create` / `memory_update` | Create memory store, configure STM/LTM strategies |
| Gateway | `gateway_create` / `gateway_target_create` | Create gateway, register tool targets |
| Runtime | `get_agent_runtime` / `update_agent_runtime` | Check agent status, update configuration |

### Verification Commands

```bash
# Check agent is running
agentcore status

# Test with sample prompt
agentcore invoke --prompt "test query"

# View logs
agentcore logs
```
